---
title: "Shared database"
description: "PostgreSQL contract between THG Community and TriBridge."
---

This bot and [TriBridge](/tribridge) are two processes serving one Discord server, and their features are
**separate**. Each has its own account links and its own bot-admin roles: linking or being staff on one bot
does not carry over to the other. They share two things only — **the PostgreSQL database** and **the
blacklist**.

**This bot owns the `public` schema.** `prisma/schema.prisma` defines every table there, and migrations create
them. TriBridge keeps its own settings, links and admin roles in its own `tribridge` schema in the same
database. This bot neither reads nor writes that schema.

## The one shared table: `Blacklist`

| Table       | This bot                                                     | TriBridge                                                   |
|-------------|--------------------------------------------------------------|-------------------------------------------------------------|
| `Blacklist` | Reads it: a listed member's interactions are refused         | Writes it with `/blacklist`, and reads it for its own commands and the relay |

TriBridge writes with plain SQL, so the table's `id` and `updatedAt` defaults must stay **database-side**: a
client-side Prisma default would make every bridge insert fail. Both sides cache the list for fifteen seconds
and **fail open** — an unreadable database blacklists nobody, because failing closed would stop both bots during
an outage.

## A one-time read of `MinecraftLink`

TriBridge reads `MinecraftLink` and `User` exactly once: on the first start of a bridge that has no link list of
its own yet, to start that list from this bot's links so nobody has to link again. The copy is saved even when
empty, so it never repeats. After that the two link lists are independent, and changing these tables no longer
affects the bridge.

## Failure behaviour

This bot treats a database failure as a real error — commands surface it through the error handler. TriBridge
loads its settings at startup and falls back to its local snapshots if the database is unreachable.
