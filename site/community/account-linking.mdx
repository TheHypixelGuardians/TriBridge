Binds a Discord user to a Minecraft account on the community bot. Linking also sets the member's nickname to
`[Knight] <Minecraft name>` and gives the link role.

These are this bot's own links. [TriBridge](/tribridge) keeps a separate list with its own `/link`, so linking
here does not change how the bridge shows a member — see [TriBridge account linking](/tribridge/account-linking).

## Commands

| Command | Who | Does |
|---------|-----|------|
| `/link` | anyone | Bind your Minecraft account: a form for the name, then a verification code |
| `/unlink [user]` | anyone / bot-admin for `user:` | Remove your link, or somebody else's |
| `/whois <user\|username>` | bot-admin | Look one up in either direction |
| `/links` | bot-admin | List every link |
| `/linkrole set\|show\|clear` | bot-admin | The role handed to linked members |

## What is stored

`MinecraftLink`, one row per member, related to `User.id` rather than to the Discord id. It holds the
canonical name Mojang returned and the account's UUID.

**The UUID is why a link survives a rename**: avatar URLs are built from it, so a member who changes their
Minecraft name keeps their head and only the stored name goes stale.

**Both directions are enforced.** One link per Discord user (`userId` is unique) and one Discord user per
Minecraft account (`uuid` is unique, and `setLink` refuses a name already claimed by somebody else). Silently
reassigning an account would let anybody wear a guild member's identity across the bridge.

Links are deliberately **not** scoped to a Hypixel guild: one link per member, whatever guild they are in.

## Verification

With verification on, `/link` proves the member owns the account:

1. `/link` opens a form asking for the Minecraft username.
2. The bot replies, only to them, with how to join the verification server and an **Enter code** button.
3. They join the server in Minecraft (Java Edition). It is online-mode, so Mojang confirms the account is
   theirs, and they are disconnected straight away with a six-digit code. Nobody loads into a world.
4. **Enter code** opens a second form. A correct code links the account and the message turns into a
   confirmation. A wrong code gets its own error, and the button keeps working.

A code works once, expires after five minutes, and only redeems for the account named in step 1. Five wrong
codes per ten minutes, then a wait: the code is the only thing between a member and somebody else's account.

A verified link **takes the account over** from anybody who claimed it before, and that member loses the link
role and the `[Knight]` nickname. Refusing would let one unverified claim lock the real owner out for good.

The server runs inside the bot. Hosts switch it on with `VERIFY_SERVER_PORT` (the port it listens on) and
`VERIFY_SERVER_ADDRESS` (what members are told to join); point an A record and a `_minecraft._tcp` SRV record
at it so members can join without typing a port.

With verification off, the name from the form is linked straight away after a Mojang check that the account
exists, and nothing more. Anyone can then link any real Minecraft name; an admin undoes a wrong one with
`/unlink user:@them`. Hypixel guild membership is not checked either way — that check lives on TriBridge's
`/link`, which needs a connected Minecraft bot.

A Mojang lookup distinguishes three outcomes, and the reply differs for each: no such account, Mojang
unreachable, and success. Collapsing the middle case into the first would tell a member they typed their own
name wrong when the truth was an outage.

## The link role

`/linkrole set <role>` names a role every linked member should have. `/link` grants it, `/unlink` takes it
back, setting the role backfills it onto everybody already linked, and `clientReady` re-syncs from the stored
links at every startup.

Two rules hold it together:

- **The role never gates the link.** `applyLinkRole` returns a result instead of throwing; every caller
  reports the failure and carries on. A missing role or a lost **Manage Roles** is a configuration problem,
  not a reason to refuse someone's `/link`.
- **The sync only ever adds.** The role may be handed out for unrelated reasons, so it is never stripped from
  someone merely because they have no link. Changing or clearing the configured role likewise leaves the old
  one on whoever has it.

Members are fetched **one id at a time**, not with a bulk roster fetch.

The bot needs **Manage Roles**, and its own highest role must rank above the link role. `/linkrole set`
refuses up front when either is untrue.

## The nickname

`/link` sets the member's nickname to `[Knight] <Minecraft name>`, and a relink replaces it. `/unlink` clears
it, but only while it is still exactly the one `/link` set: a nickname chosen since is the member's own. Like
the role, the nickname never gates the link. It needs **Manage Nicknames** and a bot role ranked above the
member's; a failure goes to the log channel. Discord never lets a bot rename the server owner.

## TriBridge

TriBridge does not read these links. It started its own list from them once, the first time it ran with links
of its own, and the two lists have been independent since. See [Shared database](/community/shared-database).
